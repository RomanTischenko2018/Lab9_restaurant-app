## Название проекта
«Ресторан» — мобильное приложение: меню, корзина и история заказов.

## Технологический стек
- **Язык:** Kotlin
- **UI:** Jetpack Compose, Material 3
- **Архитектура:** MVVM + Clean Architecture
- **База данных:** Room (SQLite)
- **Сеть:** Retrofit + OkHttp + Gson
- **Асинхронность:** Coroutines + Flow, `StateFlow`
- **Навигация:** Navigation Compose
- **Версионный контроль / CI:** Git + GitHub, GitHub Actions

## Обоснование выбора технологий
Выбрал нативную разработку под Android на Kotlin: приложение ресторана рассчитано на
Android-устройства, а нативный стек даёт лучшую производительность и официальную поддержку
Google. Flutter и React Native рассматривал, но отказался: для одной платформы они добавляют
лишний слой без выигрыша. Jetpack Compose сокращает объём шаблонного кода по сравнению с XML.
MVVM разделяет UI и логику и упрощает тестирование. Для ресторана важна связность данных
(блюдо — корзина — заказ), поэтому выбрана реляционная Room с внешними ключами и транзакциями;
Retrofit используется для подгрузки каталога блюд.

## Трудности и их решения

### Трудность 1: Оформление заказа должно быть атомарным
Заказ состоит из шапки и нескольких позиций, а корзину после этого нужно очистить. Если
приложение прервётся посередине, данные окажутся несогласованными.

**Решение:** оформление выполняется в `db.withTransaction { ... }`: снимок корзины, вставка
заказа и позиций, очистка корзины — либо всё сразу, либо ничего.

### Трудность 2: Целостность данных при удалении блюда
Если удалить блюдо из меню, оно не должно оставаться в корзине, но и история заказов не должна
меняться.

**Решение:** строки корзины связаны с блюдом внешним ключом `ON DELETE CASCADE`, а в
`order_items` название и цена копируются на момент заказа, без ссылки на блюдо.

### Трудность 3: Приложение должно работать без интернета
Меню нужно показывать даже без сети, а сервер не должен затирать правки пользователя.

**Решение:** offline-first. Начальное меню заполняется в `RoomDatabase.Callback.onCreate`,
сетевой запрос лишь добавляет блюда; уникальный индекс `remoteId` и `OnConflictStrategy.IGNORE`
не создают дублей. Ошибки сети перехватываются в репозитории и превращаются в `Result.failure`,
а UI показывает `Snackbar`.

### Трудность 4: Поиск и фильтр категории одновременно
**Решение:** запрос и категория хранятся в двух `MutableStateFlow`, объединяются через
`combine`, а `flatMapLatest` переключает подписку на новый SQL-запрос; предыдущая отменяется
автоматически.

### Трудность 5: Нет цен в открытом API
TheMealDB не содержит цен на блюда.

**Решение:** цена для блюд с сервера вычисляется из идентификатора (чисто демонстрационное
значение, вынесено в отдельную функцию и покрыто тестом); в README это указано явно.

## Что нового узнал

1. **Jetpack Compose:** состояние в UI, `LazyColumn`/`LazyRow` с `key`, `Scaffold`, фильтр-чипы, значок на иконке.
2. **MVVM + Clean Architecture:** слои presentation / domain / data, use case'ы, интерфейсы репозиториев.
3. **Room:** несколько таблиц, внешние ключи, связь «один ко многим» (`@Relation`), JOIN, транзакции, реактивные запросы через `Flow`.
4. **Retrofit:** описание API интерфейсом, `suspend`-функции, преобразование DTO в сущности.
5. **StateFlow:** единое состояние экрана, `combine`, `flatMapLatest`, `stateIn`.
6. **Тестирование:** unit-тесты ViewModel с подменой репозиториев на Fake и тесты маппинга.
7. **Git и CI:** осмысленные коммиты, автоматическая сборка и тесты в GitHub Actions.

## Тестирование
Покрыты unit-тестами (`./gradlew testDebugUnitTest`): поиск и фильтр категорий в меню,
добавление в корзину, обработка ошибки сети (`MenuViewModelTest`), преобразование данных сервера
в блюда меню (`MealMapperTest`). Репозитории подменяются Fake-реализациями, поэтому тесты
быстрые и не требуют эмулятора.
